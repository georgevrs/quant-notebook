Unit 6 · Backtesting & Research Discipline — Session 02 of 08

Build a Vectorized Backtester

Every strategy this course builds from here on gets judged the same way: turn a signal into a position, multiply by what the market actually did, and compound the result — for every asset and every day at once. Get one detail wrong, and the backtest stops grading a strategy and starts grading itself. The core move: a position may only depend on information that is already one full step old, and you prove it with a check that has nothing to do with which random seed you got lucky with.

6.2.1 What "vectorized" means

A backtester is a machine for turning a rule into a number. This session builds the version that runs in milliseconds instead of seconds, on more than one asset at a time.

Session 6.1 — What a Backtest Is (and Isn't) proved the discipline on the smallest possible case: one synthetic asset, a moving-average filter, and a plain Python loop that replayed history one day at a time. That loop is honest and easy to audit, but it does not scale — a universe of 500 assets and 20 years of daily bars is ten million loop iterations, and every one of them re-derives logic that never changes. A vectorized backtest computes the same replay as whole-array operations over the full history at once: one DataFrame of signals, one shift, one multiply, one running product — for every asset and every day in a single call. It is not a different backtest from Session 6.1 — What a Backtest Is (and Isn't)'s loop; it is the identical historical simulation, expressed so pandas and numpy can do the arithmetic instead of the Python interpreter.

The speed is not the point — it is a side effect. The real reason this course builds the vectorized version first is that a whole-array computation forces every timing decision into the open: there is nowhere to hide an accidental use of tomorrow's data inside a loop variable that quietly carries state across iterations. Session 6.3 — Build an Event-Driven Backtester rebuilds the identical strategy specification as an event loop that processes one bar at a time — slower, but closer to how a live system actually runs. Both machines must produce the same verdict on the same rule; this session is the one you will use for research, because you will run it thousands of times before you ever run the other once.

The gain compounds with scale. This session's whole experiment — two full backtests over an eight-asset universe, a 20-year statistical check, and a sweep across four lookback windows — finishes before you finish reading this paragraph. The identical arithmetic written as nested loops, one over assets and one over days inside it, would take noticeably longer even at this toy size, and at a real universe of a few thousand names it is the difference between testing an idea twenty times before lunch and testing it once a day. Speed is what makes fast, disciplined iteration possible — which is exactly why a bug that fakes a good result is so dangerous here: a vectorized backtester lets you run the wrong experiment just as quickly as the right one.

📌 Key idea — vectorized is a computation strategy, not a different rule

Nothing about "vectorized" changes what a strategy is allowed to know. The fill assumption is exactly as strict here as in a day-by-day loop — a signal computed from day t's closing price still cannot be traded against day t's own return. Vectorizing only changes how fast you can find out whether you broke that rule.

6.2.2 Signal to equity, in five steps

Every vectorized backtest, however elaborate, is the same five pandas calls in the same order. Memorize the order, not the code.

StepTypical pandas callWhat could go wrong here
1 · Signalnp.sign(returns.rolling(k).sum())using a price column that itself was built with a look-ahead join
2 · Shiftsignal.shift(lag)this session's bug: lag=0 or a missing .shift() entirely
3 · Positionsignal.div(gross, axis=0)gross exposure computed before the shift, so it uses future information too
4 · Return(position * returns).sum(axis=1)positions and returns misaligned on date or asset columns
5 · Equity(1 + strategy_returns).cumprod()summing instead of compounding returns across time

Step 2 deserves a closer look, because it is the one line this whole session is about. signal.shift(lag) moves every value down by lag rows: the value that used to sit on day t now sits on day t + lag, and the first lag rows of the result are empty. Filling those empty rows with zero — flat, no position — is a deliberate choice: a strategy with no history yet has no basis for a position, so it holds nothing rather than guessing. Everything downstream — the multiply, the sum across assets, the running product — treats that shifted DataFrame exactly like any other; none of those calls can tell the difference between a signal that was honestly delayed and one that was never delayed at all. That is precisely why the bug in §6.2.5 is so easy to introduce and so hard to spot by reading the code around it.

6.2.3 The math: weights, turnover, equity

Four short formulas carry the whole session. Read each one as "what do I know, and when do I know it."

Session 6.1 — What a Backtest Is (and Isn't) wrote the wealth of a one-asset, all-in-or-flat strategy as WˆT=W0∏t=1T(1+Pt−1Rt)\hat{W}_T = W_0 \prod_{t=1}^{T} (1 + P_{t-1} R_t), where PtP_t was 0 or 1. This session's only real change is turning that scalar position into a position per asset: a weight wi,tw_{i,t} that says how much of the portfolio's capital sits in asset ii at time tt, long or short. Sizing a ±1/0\pm 1/0 signal into a fully-invested, equally-weighted target is one line:

wi,t=si,t∑j|sj,t|w_{i,t} = \frac{s_{i,t}}{\sum_j |s_{j,t}|}

where si,ts_{i,t} is the raw signal. Take a concrete day with three assets and signals of +1, −1 and 0. The denominator sums the absolute values, |1|+|−1|+|0|=2|1| + |-1| + |0| = 2, so the target weights are +50%, −50% and 0% — a fully-invested, dollar-balanced book no matter how many of the three signals happen to be active that day. Two active assets would split the book fifty-fifty; one active asset would put the whole 100% on it alone. This is one specific, simple sizing rule among many — later sessions weight by conviction, by volatility, or by an optimiser's output instead of splitting evenly — but every one of them still answers the same question this formula answers: given today's signals, what fraction of capital goes where.

The weight the strategy actually holds on day tt is not wi,tw_{i,t} — it is the weight decided signal lag periods earlier, written wi,t−lagw_{i,t-\text{lag}}. The honest default is lag = 1. That single subscript is the entire discipline this session is about; everything else below is bookkeeping around it.

Sum the held weights times what each asset actually returned, and you have the portfolio's simple return for the day. Compounding it forward gives the equity curve — reusing Session 6.1 — What a Backtest Is (and Isn't)'s Wˆ\hat{W} notation for a simulated wealth path:

Rt=∑iwi,t−lagRi,t,Wˆt=Wˆt−1(1+Rt)=∏τ≤t(1+Rτ)R_t = \sum_i w_{i,t-\text{lag}}\, R_{i,t}, \qquad \hat{W}_t = \hat{W}_{t-1}(1 + R_t) = \prod_{\tau \le t} (1 + R_\tau)

The last piece, turnover, measures how much of the book changes hands from one day to the next. This session uses the one-way convention: half the sum of absolute weight changes, so a book that flips completely from one asset to another in a single day shows 100% turnover, not 200%:

TOt=12∑i|wi,t−wi,t−1|\mathrm{TO}_t = \frac{1}{2}\sum_i \left| w_{i,t} - w_{i,t-1} \right|

Walk the three-asset day from above forward one step to see why the one-half belongs there. Suppose the book (+50%, −50%, 0%) moves the next day to (0%, −50%, +50%): the short stays put, and the long rotates from the first asset to the third. The absolute weight changes are 0.5, 0 and 0.5 for the three assets, summing to 1.0; halving that gives 50% turnover, matching the plain-English answer that half the book — one asset's worth of exposure — actually traded. Without the one-half, the identical rotation would be reported as 100% turnover even though only half the capital moved. Grinold & Kahn's convention, cited below, exists precisely so that a number called "turnover" means the fraction of the portfolio that changed hands, not a sum that counts every trade as both a sale and a purchase.

🧭 Margin note — weights, not shares

Everything here works in target weights (a fraction of capital), never share counts or contract sizes. A real account has to translate a weight into an integer number of shares given its NAV — pure bookkeeping, and out of scope here; the discipline this session teaches applies identically either way.

6.2.4 In code: a backtester in ten lines

Three small functions carry §6.2.2's whole pipeline. Run correctly, they produce an unremarkable, believable backtest — which is exactly the point of building the honest version first.

# position sizing: a +-1/0 signal to a fully-invested, equally-weighted target
def equal_weight_positions(signal):
    gross = signal.abs().sum(axis=1)
    return signal.div(gross.replace(0.0, np.nan), axis=0).fillna(0.0)

# the backtest itself: signal -> lagged position -> return -> equity, one call
def vectorized_backtest(returns, target_weights, lag=1):
    position = target_weights.shift(lag).fillna(0.0)
    strat_returns = (position * returns).sum(axis=1)
    equity = (1.0 + strat_returns).cumprod()
    return {"position": position, "returns": strat_returns, "equity": equity}

Every idiom above has a direct polars equivalent — pl.col("signal").shift(1) in place of signal.shift(1), .sum_horizontal() in place of .sum(axis=1) — and the same reasoning applies line for line. This course writes labs in pandas because the rest of the codebase does, not because the discipline is pandas-specific: the shift is what matters, not the library that executes it.

On an 8-asset synthetic universe with volatilities from 12% to 30% and zero drift on every asset — a fair game, no true edge anywhere in the data by construction — a 1-day lookback signal (lag=1, the honest default) turns in an entirely forgettable two simulated years: CAGR −6.32%, Sharpe ratio −0.77, a real drawdown of −16.96%, turnover of about 130× a year. Nothing here should impress anyone, and it doesn't — which is the correct result on data with no edge in it.

Zero drift on every asset is not a simplification made for convenience — it is the whole reason to test on synthetic data in the first place. On real prices you can never be sure whether a good-looking backtest found a real, if modest, effect or simply got lucky; on data built with exactly zero true edge, any measured edge has exactly one possible source: a bug in the backtester. That is the same logic Session 6.1 — What a Backtest Is (and Isn't) used with its single asset, generalised here to a universe wide enough that an accidental edge would have to survive averaging across eight independent draws rather than one.

Two simulated years is short enough that a Sharpe of −0.77 could easily be noise rather than proof of "no edge." A separate, independent 20-year run of the same universe lets us test that properly. The standard error of the Sharpe ratio from 20 years of daily data is 0.224, so a true Sharpe of zero should show an estimated Sharpe within about 0.894 of zero, four standard errors either way. The honest backtest's 20-year Sharpe comes in at 0.17 — comfortably inside that band, exactly as it should be on data built to contain no edge at all.

Four standard errors, rather than two or three, is a deliberate margin, not a stylistic choice. A course full of labs each running dozens of statistical checks is, collectively, running hundreds of them, and at a two-standard-error threshold a meaningful fraction of perfectly correct results would flag as suspicious purely by chance. Session 6.7 — Overfitting Statistics: PSR, DSR, MinTRL & PBO makes this multiple-testing problem the centre of an entire session; here it is enough to note that a four-standard-error band keeps a single false alarm rare without needing that later machinery.

6.2.5 The one-line bug that fakes a 56 Sharpe

Delete four characters from the code above — .shift(1) becomes nothing — and the identical signal on the identical data turns into the best backtest you will ever see. It is also completely fake.

Session 6.1 — What a Backtest Is (and Isn't) already showed a mild version of this: a slow moving-average filter, applied to its own close instead of the prior one, turned a Sharpe of 0.03 into 1.49. That signal changes only gradually, so the leak from one day's own return is small. Push the same mistake to its logical extreme — a signal that looks back just one day — and the leak stops being small.

Run both lines on the same 8-asset universe from §6.2.4. Removing the shift alone — same signal, same data, same universe — reports a CAGR of 1,283%, a Sharpe of 56.2, and a drawdown of exactly 0.00% — not "small," exactly zero, every single day, for two straight years. That last number is not a statistical fluke: because the naive weight on each asset is the sign of that same asset's same-day return, the naive payoff is sign(R) * R = |R|, which cannot be negative. A strategy that never has a single losing day is not lucky — it is look-ahead bias wearing a Sharpe ratio as a disguise.

The identity behind that zero is short enough to check by hand: for any number xx, sign(x)×x\mathrm{sign}(x) \times x equals |x||x|, and an absolute value can never be negative. The naive weight on an asset is, up to the equal-weight denominator, the sign of that same asset's same-day return, so the naive payoff on that asset is exactly the absolute value of its own return — a coin that pays you for landing on either heads or tails. Averaging several such coins across eight assets does not undo the trick; it only makes the resulting equity curve smoother, which is exactly why fig 6.2.4's naive line looks less like noise and more like a ruler.

Notice what does not change between the two rows: turnover is about 130× a year either way, because both versions hold the same weights — only the day they are allowed to apply them differs. A turnover report or a trade log would never catch this bug; only the timing of the join would. Concretely, on the honest strategy's single worst day it lost −1.35% — and the naive version, trading that exact same crash against itself, reports a gain of 1.36% on that identical day. Session 6.4 — The Bias Hall of Fame catalogues every other classic way a backtest lies — survivorship, data snooping, stale and untradable prices, and the Session 4.2 — Point-in-Time Data & Data Biases version of look-ahead bias, which lives in the data rather than in the code. This one lives entirely in a single misaligned index.

None of this requires careless code. pandas is forgiving by design — it aligns DataFrames on their index automatically, broadcasts a Series across columns without complaint, and never refuses to multiply two frames just because one of them silently carries information from the wrong day. That forgiveness is usually a feature. It is also why an accidental same-day merge, a resample that closes its window on the wrong side, or a rolling function computed before instead of after a shift, all fail in exactly the way this deliberately planted bug does — quietly, and with a result that looks better, not worse.

⚠️ Pitfall — "it ran without an error, so the shift must be fine"

A vectorized backtest with a missing or wrong shift never raises an exception. Every DataFrame lines up, every column multiplies cleanly, and the number that comes out is not just plausible — it looks like the best result you have ever produced. Treat a backtest with zero drawdown, or a Sharpe far outside anything in Session 6.1 — What a Backtest Is (and Isn't)'s or this session's honest runs, as a bug report on your indexing before you treat it as a discovery.

6.2.6 Does a longer lookback save you?

A slower signal leaks less of tomorrow's answer into today's decision — but "less" is not "zero," at any lookback anyone actually trades.

A signal built from a k-day lookback sums k days of returns, one of which is day t itself. An un-shifted signal therefore leaks a 1/k share of the day's own return into that day's decision — shrinking, by construction, as k grows:

The 20-year universe from §6.2.4 confirms this directly: the naive-minus-honest Sharpe gap shrinks steadily as the lookback grows, but it is still large at a 60-day lookback — a window most trend-following desks would call "slow."

Real time-series-momentum signals, of the kind Moskowitz, Ooi & Pedersen (2012) study across 58 futures markets (below), typically look back one to twelve months — roughly 21 to 252 trading days — squarely inside and beyond the range this table tests. Their signal also differs from this lab's sign-only toy in a way worth naming: they scale the position by realised volatility rather than sizing every asset equally. That changes exactly how much this bug would move the final Sharpe ratio; it changes nothing about whether the bug exists, because the leak lives in the shift, not in the sizing.

Every naive column sits far above it — the smallest gap tested, at a 60-day lookback, is still more than five times the width of the 4-standard-error band from §6.2.4. A slower signal is not a safer one to leave unshifted; it is only a less dramatic advertisement of the same mistake.

🧭 Margin note — one line, always

There is no lookback long enough to make skipping .shift(lag) a reasonable trade-off. The line costs nothing to write and removes the leak entirely, regardless of how the signal is built — treat it as non-negotiable rather than something to weigh case by case.

6.2.8 Glossary · Check yourself · Go deeper

Vectorized backtest — a backtest computed as whole-array operations over the full price and return history at once (pandas/numpy), rather than looping day by day; identical in what it assumes to a day-by-day replay, only faster.
Position — the size and direction of a strategy's exposure to one asset at a point in time, expressed here as a weight: a fraction of the portfolio's capital, positive for long and negative for short.
Turnover — how much of a portfolio's weights change from one period to the next; reported here one-way, as half the sum of absolute weight changes, so a complete switch from one asset to another counts as 100%, not 200%.
Signal lag — the number of periods that must separate the information a signal uses from the position built from it, so a backtest never holds a weight decided with data it could not yet have seen.
Equity curve — the running value of $1 invested in a strategy since its start: the cumulative product of one plus each period's return.

Check yourself

1. A colleague's vectorized backtest computes positions = signal and then returns = (positions * asset_returns).sum(axis=1), with no .shift() anywhere. What information is day t's position implicitly using, and when would that information actually exist in a live account?
Day t's signal was computed from data available only at the close of day t — which is also when day t's return becomes known. The backtest is applying day t's decision to day t's own return as if the decision preceded it, but in a live account you cannot see a day's closing price, and therefore cannot finish computing that day's signal, before that same day's return has already happened.
2. A fully-invested long-short book flips overnight from 100% long asset A to 100% long asset B. Using this session's one-way convention, is the turnover 200% or 100%? Why?
100%. One-way turnover is half the sum of absolute weight changes: |ΔA| + |ΔB| = |−1| + |+1| = 2, and half of that is 1, i.e. 100%. The convention counts the fraction of the book that traded, not a sum of every buy and every sell counted separately — which is why the "one-way" name matters.
3. A backtest reports a Sharpe ratio of 56 and has never had a single losing day across 20 simulated years. Should you be impressed? What would you check first?
No — check the shift between signal and position first. A real strategy exposed to any risk cannot have literally zero drawdown; the combination of an extreme Sharpe ratio and a perfectly smooth equity curve is closer to a fingerprint of look-ahead bias than to evidence of skill.
4. If forgetting to shift barely moves the Sharpe ratio for a signal with a 250-day lookback, is it safe to skip the shift for that particular signal?
No. The bias shrinks toward zero as the lookback grows but, per §6.2.6's data even at a 60-day window, never reaches it. Deciding case by case whether a given signal is "slow enough" to skip the discipline replaces a free, always-correct habit with a judgment call that can be wrong — there is no benefit to skipping it even when the visible damage is small.
5. Two assets both show a signal of exactly 0 today (flat). What happens to the portfolio's weights that day under equal_weight_positions(), and why doesn't dividing by zero crash the code?
If every asset's signal is 0, gross exposure (the sum of absolute signals) is 0 for that day. The function replaces a zero gross with NaN before dividing, so the division produces NaN instead of raising an error, and the final fillna(0.0) turns that into an explicit, fully-cash position for the day — exactly what "no signal anywhere" should mean.
