6.3.1 Two ways to replay history

A backtest replays history to see what a strategy would have done. Session 6.2 — Build a Vectorized Backtester replays it as one big array computation; this session replays it one event at a time. Both are correct — they answer different questions.

Session 6.1 — What a Backtest Is (and Isn't) defined a historical simulation as mechanical: two people coding the same strategy specification should get identical trades. Session 6.2 — Build a Vectorized Backtester made that mechanical replay fast — a vectorized backtest holds the whole price history as one array and computes position, return and equity curve in a handful of array operations, which is exactly why it can sweep thousands of parameter combinations overnight. This session makes the same replay realistic: an event-driven backtest processes history as a stream of discrete events — a new price, a decision, an order, a fill — through the same object shapes a live trading system uses. Nothing here says vectorized backtesting is wrong; it is the right tool for search. Event-driven backtesting is the right tool for anything whose behaviour depends on what happens between two data points, and for anything you eventually want to run live.

Neither architecture is a defence against bad data or a badly specified rule. Session 6.4's look-ahead, survivorship and stale-price bugs infect a vectorized backtest and an event-driven one equally, because they live in the data and the specification, not in the loop shape. Architecture buys you exactly two things: the ability to express path-dependent orders cleanly (§6.3.5), and a strategy you can eventually run for real without rewriting it (§6.3.7). Expect the event loop to make an honest backtester easier to build, not to make a dishonest one impossible.

📌 Key idea — the payoff is shape, not speed

An event-driven backtest is deliberately built out of the same pieces a live system needs: an order, a fill, and portfolio state that only ever changes in response to one of those. Moving from backtest to live becomes a matter of swapping where events come from, not rewriting the strategy. That property is backtest–live parity, and it is the reason Unit 15 builds directly on this session's vocabulary.

6.3.2 The event loop, tick by tick

Strip away the trading vocabulary and an event loop is a generic pattern: a queue of typed messages, and a loop that pops the oldest one and hands it to whatever reacts to that type.

The pattern is old and general — it is how GUIs, network servers and message brokers are built, and Hohpe & Woolf's Enterprise Integration Patterns catalogues it in full for distributed systems. A backtester needs only four pieces of it: a market event announcing a new price, the strategy's decision, an order recording what it wants to trade, and a fill recording what actually happened. Everything the loop does is one of: react to a new price, decide, submit an order, or apply a fill.

A GUI's loop reacts to MouseClick and KeyPress and produces screen updates; a web server's reacts to Request and produces Response; this backtester's reacts to MarketEvent and produces OrderEvent. Swapping the event type is the entire difference between the three — the loop, the queue, and the discipline of handling one message before asking for the next are identical. That is what makes the pattern worth learning once and reusing, rather than reinventing per project.

In this lab the queue is, quite literally, the market feed: run_event_loop pops the next MarketEvent from a plain deque, and everything that one tick causes — a stop check, a decision, an OrderEvent, its FillEvent — is settled with ordinary function calls before the loop asks the feed for the next tick. A larger engine would push those follow-on events back onto one shared queue so several instruments or several strategies could interleave; for one strategy watching one instrument, that generality buys nothing but a new way to get the ordering wrong, so this lab keeps it direct. NautilusTrader's actual event bus implements the general version, in Rust, for exactly the case where the generality earns its keep.

💡 Tip — the queue can hold anything

Nothing about this loop knows it is fed by history. Swap the queue's source for a live broker socket and the strategy, order and fill code do not change — the mechanism behind §6.3.7's backtest–live parity.

6.3.3 Orders, fills and portfolio state

Three small objects carry all the state. Get their fields right and the rest of the engine is bookkeeping.

An order is a request, not yet a trade: it records a side (buy or sell), a type (fill now, or fill only if a condition is met), and, for a conditional order, the trigger price. A fill is the fact that a trade happened: a price, a quantity, and a commission — nothing about intent survives into a fill, only what occurred. Portfolio state is the running account: cash, shares held, and the equity curve that a MarketEvent re-prices and a FillEvent changes. This is the same separation a real order management system keeps, and for the same reason — an order can be rejected or sit unfilled, so the portfolio must never move until a fill says it can. An OMS is a state machine: it only transitions on an event, never on a wish. This lab's OrderEvent only ever reaches two end states — filled, or still resting — but a production order lives through more of them (submitted, partially filled, rejected, cancelled), and every one of those is still just a named transition triggered by an event nobody was allowed to skip.

Marking the portfolio to market is one identity: wealth is cash plus the value of what you hold at today's price. Writing shares held as ntn_t and cash as CtC_t:

Wt=Ct+ntPtW_t = C_t + n_t P_t

Every MarketEvent recomputes this once, using whatever n_t the last fill left behind — which is exactly why a fill must be applied before the next price is marked, not after (§6.3.4 shows what breaks if you get the order wrong).

The order_type field is deliberately open-ended. This lab implements only MARKET (fill now) and STOP (fill once price crosses a trigger), but a limit order — rest until a better price is on offer, not a worse one — is the same object with one different comparison inside ExecutionHandler, not a different architecture. Whichever order types Session 2.1 introduced as market mechanics, this engine can hold as data.

🧭 Margin note — the fill assumption, made explicit

Session 6.1 — What a Backtest Is (and Isn't) named the fill assumption: at what price, and after what delay, a trade is assumed to execute. This lab fills every MARKET order at the current event's price and sets commission to zero throughout — the simplest honest assumption, priced properly in Session 6.5 — Transaction Costs & Capacity. The risk-free rate is 0%: cash earns nothing while flat.

6.3.4 In code — and does it agree?

Four classes and one loop are enough. Run them on the same data and the same rule Session 6.2 uses, and there is only one honest answer.

# the four types: a market event, an order, a fill, and the portfolio it updates
class Portfolio:
    def on_fill(self, fill):
        if fill.side == "BUY":
            self.shares += fill.quantity
            self.cash -= fill.quantity * fill.price + fill.commission
        else:
            self.shares -= fill.quantity
            self.cash += fill.quantity * fill.price - fill.commission

    def mark_to_market(self, price):
        equity = self.cash + self.shares * price
        self.equity_curve.append(equity)
        return equity

The loop itself is a deque of MarketEvents. Popping one marks the portfolio, checks any resting stop, and — using only data known before this tick — decides whether to submit an OrderEvent, whose fill is applied before the loop asks for the next tick:

# market_events is the queue; everything one tick causes is settled before the next tick is popped
while market_events:
    ev = market_events.popleft()
    portfolio.mark_to_market(ev.price)
    stop_fill = execution.check_resting_stop(ev.day, ev.price, portfolio)
    if stop_fill: portfolio.on_fill(stop_fill)
    if target_position[ev.day + 1] != portfolio.invested:
        fill = execution.submit(order, ev.price, portfolio)
        portfolio.on_fill(fill)

The rule under test is Session 6.2's own construction, narrowed to one instrument so the loop only needs one order book to read: the least volatile of its eight fair-game (zero-drift) assets, and its own 60-day lookback signal, long only. The vectorized backtest shifts that signal by one day and multiplies; the event loop above reaches the same OrderEvent decisions from the same data, one tick later in wall-clock terms but not one bit later in information. Run 1,500 simulated days through both:

The vectorized engine ends at $0.8335 per dollar invested; the event loop ends at $0.8335. The largest gap between the two equity curves, on any day, is 3.77e-15 — floating-point noise, not a discrepancy. This is not a Monte Carlo result to be trusted within some tolerance: both engines do the same arithmetic on the same numbers, so they either match to machine precision or one of them has a bug.

That is a general technique, not a backtesting trick. Whenever two implementations claim to compute the same thing, feeding both identical input and demanding bit-for-bit agreement is a far stronger check than reading either one's output and deciding it looks plausible. A vectorized backtest and an event loop are about as independent as two implementations of one specification get — one is array algebra, the other is a small state machine — which is exactly why their agreement here is worth something.

6.3.5 What a vectorized backtest can't see

A resting order is the case where the two architectures stop being interchangeable.

A Session 2.1-style stop order is a standing instruction: sell if the price ever trades at or below a level, whenever that happens. It only means something if something is watching continuously after the order is placed — it is path-dependent, not a function of the day's return alone. A vectorized backtest has no "continuously": it has one row per bar. The best it can do is compare a bar's close to the stop level once per bar, which makes it blind to whatever the price did between two closes. The event loop needs no new machinery for this — ExecutionHandler.check_resting_stop already runs on every MarketEvent in §6.3.4 — so extending it means feeding it a finer stream of the same event type, not writing new code.

One simulated path makes the mechanism concrete: a position held through a rough patch, with a stop resting 8% below the entry price, checked on every one of twelve sub-daily ticks instead of once at the close.

On this path the unprotected position ends at $0.63 per dollar invested; the stopped-out version ends at $0.91. One path is an anecdote, not evidence — the real question is how much a stop's execution quality degrades if it can only be checked once a day, the way a vectorized backtest would have to check it. Across 6,000 simulated paths over a 60-day holding window, 3,496 paths breach the stop at some point. Checking only at the close misses the breach entirely on 5.2% of them — the price dips below the stop intraday and recovers by the close, so a close-only check never even knows to react. On the 3,314 paths where both methods do trigger, checking only at the close executes, on average, 80.1 basis points further past the intended stop level than checking every tick (31.4 bps of overshoot checking every tick, vs. 111.6 bps checking once a day) — a gap of 47.9 standard errors from zero, not a coincidence of one draw.

Nothing stops someone from bolting a "stop" onto a vectorized backtest by comparing each day's close to a level. But that is a materially different, worse-executing order than the one a live broker actually offers, and the vectorized code has no natural place to remember "already stopped out, stay flat" without reaching for a loop — at which point it is not vectorized any more. The event loop expresses the path-dependent order directly, because it was already built to look at one event at a time.

📌 Key idea

A resting order is a claim about what happens between observations. A vectorized backtest has no "between" — only rows. An event-driven backtest's unit of time is whatever granularity you feed it, which is why it extends to path-dependent orders and a vectorized backtest, however cleverly written, does not.

6.3.6 The pitfall: a queue that still peeks

An event loop looks disciplined by construction. It is only as disciplined as the objects passed through it.

The whole promise of §6.3.1 — that this architecture cannot look ahead — depends on one thing: the strategy must receive nothing but the current event. It is easy to write an event-driven-looking backtester that quietly fails this. If a Strategy object is constructed with the entire price array (Strategy(prices)) and only also reacts to MarketEvents, nothing forces it to use event.price instead of prices[t + 5]. The loop still pops events in order, the code still looks like an event loop, and the equity curve can still look completely plausible — the bug does not announce itself in the output, because a look-ahead bug generally makes results better, not obviously broken.

This is a specific, code-shaped instance of a disease with its own name: Session 4.2 calls it look-ahead bias, and shows it quietly inflating performance in backtests that have no event loop anywhere in sight. The event loop does not cure the disease — it just relocates where the bug has to hide, from an unlagged array shift to a constructor argument.

⚠️ Pitfall — "an event loop can't look ahead"

An event loop makes look-ahead awkward, not impossible. The guarantee only holds if every object the strategy can reach was constructed from data available at or before the current event — no stored reference to the future rows, no global holding the full history. In code review, read the constructor arguments of the strategy class before you trust the loop around it.

6.3.7 Backtest–live parity: why the shape matters

The reason to pay for a slower architecture is what it lets you reuse later.

A vectorized backtest's core operation — multiply a whole column by another whole column — has no live equivalent: a live system never has "the whole column," only the next tick. So going from a vectorized research backtest to a live strategy means a rewrite, and a rewrite is where new bugs live. An event loop's core operation — react to one event, maybe emit another — is already what a live system does, message by message. Backtest–live parity is the practice of keeping the strategy, order, fill and portfolio code identical between the two, and swapping only the two pieces that touch the outside world: where MarketEvents come from, and how OrderEvents get turned into FillEvents.

A team that validates a signal in a vectorized research notebook and then asks an engineer to "productionise it" has, whether anyone says so out loud, just created a second, unaudited specification of the strategy — the two now agree only as well as the two people who wrote them happened to agree. Backtest–live parity's real saving is not runtime speed; it is deleting that second specification, and the translation bugs that come with it, entirely.

This is not a hypothetical benefit. NautilusTrader — the open-source engine Session 15.2 — Backtest-to-Live with NautilusTrader is built around — states its core design goal in exactly these terms: the same strategy and execution-algorithm code runs across backtest and live systems, which is what removes the translation step (and the bugs it introduces) between "it worked in research" and "it works with real orders." Session 15.1 — Architecture of a Live Trading System gives the production version of this diagram a proper name — order management system, execution management system — but the shape is the one you just built.

6.3.8 Try it

Watch the two engines agree, then make them disagree on purpose — breaking something correctly on purpose is one of the fastest ways to trust that it was doing anything at all.

Reading a passing assertion tells you the code ran; it does not tell you the assertion was testing what you think it was testing. The two exercises below are the same check run in both directions: first confirm the agreement is as exact as claimed, then remove the one line responsible for the stop's protection and watch the specific number it protects collapse. If a change to a single, named line doesn't move the one number it should move, the line was not doing what the comments said.

6.3.9 Glossary · Check yourself · Go deeper

event-driven backtest — a historical simulation that replays market data one event at a time through the same strategy, order, fill and portfolio code a live system uses, instead of computing the whole history as arrays at once.
event loop — the loop that pops the next event off a queue, hands it to whatever reacts to that type, and keeps going until the queue is empty.
order — an object recording what the strategy wants to trade: a side, a type, and any trigger price. A request, not yet a trade.
fill — an object recording that an order actually executed: the price, the quantity, and any commission.
portfolio state — the running record of cash, shares held and mark-to-market equity, changed only by a fill and re-priced by every market event.
backtest–live parity — using the same strategy, order, fill and portfolio code in backtest and in live trading, so only the data source and the execution handler change.

Check yourself

1. You have swept 5,000 parameter combinations overnight with Session 6.2's vectorized backtester. A colleague asks you to also test each position carrying a 5% trailing stop. Should you bolt the stop onto the vectorized sweep, or reach for the event loop?
The event loop. A trailing stop needs to remember the running extreme price and whether it has already fired — state carried from tick to tick — which an array of shifted columns has nowhere to hold. Keep the plain sweep (no stop) vectorized; add the event loop only for the run that needs path-dependent state.
2. In §6.3.2's loop, why must the fill from a decision made while processing day t−1's tick be applied before day t's market event marks the portfolio? What would §6.3.4's parity check show if you got this backwards?
Day t's return belongs to whatever position was decided using data through day t−1 — that position must already be in place before day t's price is marked, or the wrong day earns the wrong return. Get the order backwards and parity_max_abs_diff stops being floating-point noise (~1e−15) and becomes a real, visible mismatch against the vectorized answer — exactly the kind of bug an exact-agreement test exists to catch.
3. Your strategy emits an OrderEvent to buy, and the process crashes before a FillEvent is produced. What does the portfolio's state show, and why does that matter operationally?
Cash and shares are exactly what they were before — the portfolio only changes on a FillEvent, never on an order alone, because an order is a request that can be rejected, partially filled, or lost. That separation is why a real order management system tracks working orders separately from the position: it must never assume a trade happened until a fill confirms it.
4. Two students each write an event loop. Student A's Strategy class takes the full price array in its constructor; Student B's only receives event.price inside a market-event handler. Whose design can silently reintroduce look-ahead bias, and how would you catch it in review?
Student A's. Holding the whole array lets the strategy index ahead of the current tick, and the resulting equity curve can still look completely plausible — a look-ahead bug usually makes results look better, not obviously wrong. You catch it by reading the constructor signature in review, not by trusting the numbers.
5. Session 15.2 will point a live broker feed at classes built in this lab. Which pieces stay untouched, and which must be swapped?
The MarketEvent/OrderEvent/FillEvent types and the strategy and portfolio logic stay exactly as written. What changes is where MarketEvents come from (a stored price array vs. a live socket) and what turns an OrderEvent into a FillEvent (a simulator vs. a real broker API) — that swap, and nothing else, is backtest–live parity.
