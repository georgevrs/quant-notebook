The Research Storage Stack

A research desk's data starts as one CSV and, within a year, becomes either one file too big to open or a directory of millions of tiny ones. Parquet, Arrow, DuckDB and polars are the free, local stack that sits between those two failure modes — the stack every later lab in this course reads and writes. Store data column-by-column, split it by what you actually filter on, and let the engine skip everything else.

4.5.1 The stack, in one picture

Every session so far has read a handful of prices from a CSV or built them in memory. A real research desk stores years of bars for thousands of symbols, and a CSV stops working long before the data gets interesting.

A CSV (or a pickle, or a single giant Parquet file) is row-oriented: each record sits together on disk, in the order it was written. That is exactly right for a broker statement — one row, all its fields — and exactly wrong for research, where a typical question touches one or two columns (say, closing price and volume) across millions of rows. Reading a row-oriented file for that question still has to walk past every other column on every row. Columnar storage flips the layout: every column is stored contiguously, so a query that needs two columns out of thirteen can skip the other eleven without ever decoding them.

Four pieces make this practical without a database server. Parquet is the columnar file format on disk: compressed, self-describing, and splittable into many files. Apache Arrow is the columnar format for data sitting in memory — not a file format, a shared in-memory layout that lets one process hand data to another (or to itself, across libraries) without copying or re-encoding it. DuckDB is an embedded SQL engine that reads Parquet directly and executes on top of Arrow. polars is a DataFrame library, written in Rust, that does the same job as pandas but is built around Arrow and a multi-threaded, lazily-optimised query engine from the start. None of the four needs a server, a port, or an admin: `pip install` (already done for this course) is the whole deployment.

📌 Key idea — the format matters before the engine does

DuckDB and polars are fast partly because they are well-written, but mostly because columnar storage plus compression means there is simply less to read. Section 4.5.4's lab shows the same query on the same data getting faster twice: once from switching CSV to Parquet, and again — by a much larger margin — from adding partitioning and letting the engine skip files it doesn't need.

4.5.2 How a lazy, partitioned query runs

"Partitioned" and "lazy" are not conveniences — they are the two mechanisms that let an engine avoid reading data at all. Neither works without the other.

Partitioning means writing a dataset as many files, laid out in directories named after column values — year=2012/sector=SEC03/part.parquet is Hive-style partitioning, the convention DuckDB, polars and Spark all read without configuration. A query that filters on the partitioned columns can skip entire directories before opening a single file: this is partition pruning, and it is decided from directory names alone, before any Parquet footer is even read.

Lazy evaluation is the other half. polars' scan_parquet does not read anything — it returns a LazyFrame, a description of the computation, which you then narrow with .filter(...) and .select(...) before finally calling .collect(). Because the whole query is visible before any of it runs, polars' optimiser can push the filter down to the scan itself (only decompress rows that can possibly match) and push the column selection down too (only decode columns the query actually names) — predicate pushdown and column pruning. DuckDB reaches the same result from SQL: a WHERE clause on partition columns prunes directories, and the columns named in SELECT are the only ones decoded. pandas' read_parquet, by contrast, is eager — it decodes the whole file into a DataFrame before you get to write a single .loc[...].

FormatSize on diskWrite time
CSV, one file207 MB9.5 s
Parquet, one file (no partitioning)76 MB1.04 s
Parquet, partitioned (50 files)100 MB0.42 s

The columnar format alone shrinks the file to 2.7× smaller than the CSV holding the identical rows — before partitioning or querying enter the picture at all.

4.5.3 Partitioning strategy and the arithmetic of pruning

A partitioning scheme is a bet on how you will filter later. Get it right and most queries touch a sliver of the data; get it wrong and you have either one file too big to skip, or too many files to open.

Partition on the columns your queries actually filter on — for a research panel that is usually date (or a coarser bucket of it, like year or month) and, when the query is often about one slice of the universe, something like sector or exchange. Partitioning on a column with millions of distinct values (a trade ID, a raw timestamp to the microsecond) does the opposite of helping: it turns every partition into a handful of rows and every directory listing into a bottleneck. As a working rule, aim for partitions in the tens of megabytes to low hundreds — small enough to skip, large enough that opening one is not mostly overhead.

The saving from partitioning multiplies with the saving from column pruning, because they cut along different axes — one skips files, the other skips fields within the files that remain:

bytes scannedbytes total≈partitions touchedpartitions total×columns touchedcolumns total\frac{\text{bytes scanned}}{\text{bytes total}} \;\approx\; \frac{\text{partitions touched}}{\text{partitions total}} \;\times\; \frac{\text{columns touched}}{\text{columns total}}

This is a back-of-envelope estimate, not an exact one — Parquet compresses columns individually, so a column of tightly-clustered floats can compress far better than a column of high-cardinality strings, and the ratio above assumes every column costs the same. It is still the right order of magnitude: the lab's query touches 2% of the partitions and 38% of the columns, for an estimated 0.77% of the bytes — and §4.5.4 shows that estimate landing in the same neighbourhood as the wall-clock speedup actually measured.

Partition granularityWhat happensCost
None — one file for everythingEvery query, however narrow, opens the whole fileNo pruning at all; only column pruning helps
By year and sector (this lab)A date-and-universe filter skips almost every file50 files here, each tens of MB — a sensible middle
By year, sector and symbolEvery query still finds its file quicklyThousands of tiny files: metadata and open() overhead start to dominate (§4.5.5)
🧭 Margin note — partition columns are metadata, not always real columns

Hive-style writers pull the partition values out of the data and encode them only in the directory names; hive_partitioning=true tells DuckDB and polars to read them back out of the path and re-attach them as columns on the way out. Filtering on a partition column is therefore closer to a directory listing than a table scan.

4.5.4 The same query, four ways

One question — for one sector, in one year, the average close and total dollar volume of every symbol — answered four ways on the same panel. Only the storage layout and the engine change.

The panel underneath: 1,500 symbols across 10 sectors, 5 years of simulated daily bars with a few extra columns (open, high, low, vwap, trade count, bid, ask) a query never needs — 1,890,000 rows in all.

The naive way reads everything, in a text format, before it can even start filtering:

# naive: full file, all 13 columns, then filter in memory
df = pd.read_csv("panel.csv", parse_dates=["date"])
sub = df[(df["year"] == YEAR) & (df["sector"] == SECTOR)]

Switching to a single Parquet file changes only the format — still one file, still a full scan — and is already faster because the columns are compressed and typed rather than re-parsed from text. Switching to a partitioned Parquet dataset and asking DuckDB to do the filtering changes the shape of the work entirely:

# DuckDB: the WHERE clause prunes partitions before it decodes anything
con.execute("""
    SELECT symbol, avg(close) AS avg_close, sum(close * volume) AS dollar_volume
    FROM read_parquet('panel_partitioned/**/*.parquet', hive_partitioning = true)
    WHERE year = 2012 AND sector = 'SEC03'
    GROUP BY symbol
""").df()

polars reaches the same plan through its lazy API rather than SQL — the point of scan_parquet returning a LazyFrame is that nothing below has executed yet:

# polars: still just a plan until .collect() — filter/select push down into the scan
lf = pl.scan_parquet("panel_partitioned/", hive_partitioning=True)
result = (lf.filter((pl.col("year") == YEAR) & (pl.col("sector") == SECTOR))
            .group_by("symbol")
            .agg(pl.col("close").mean(), (pl.col("close") * pl.col("volume")).sum())
            .collect())

All four return the identical 150 rows — the lab asserts numerical agreement to four significant figures before it trusts any timing number. What changes is only the time it takes to get there:

MethodWall timevs. naive CSV
pandas + CSV (full scan)2,162 ms—
pandas + 1 Parquet file (full scan)347 ms7.2× slower than partitioned DuckDB
DuckDB + partitioned Parquet48.1 ms45× faster
polars (lazy) + partitioned Parquet32.7 ms66× faster
🧭 Margin note — benchmarks are honest only with their caveats stated

These are single-machine, single-run wall-clock times; disk cache, core count and background load all move the absolute numbers, and the very first query DuckDB or polars ever runs in a process pays a one-off thread-pool warm-up of about a second. The lab reports the steady-state time after that warm-up and takes the minimum of several repeats — what stays robust across machines is the shape of the result (two orders of magnitude), not the exact millisecond.

4.5.5 Where people go wrong: one file, or one file per row

The two failure modes are mirror images: too little structure, and every query pays for everything; too much structure, and the filesystem itself becomes the bottleneck.

The second failure is subtler and hits people who took the first lesson too literally: if partitioning by year and sector helps, why not also partition by symbol, so every query finds an even smaller file? The lab tests this directly — it takes the exact slice one query wants and writes it two ways, as the single file it already is, and again split into one tiny file per symbol. Reading the identical bytes is 19.4× slower as 150 tiny files than as one: opening a file, reading its footer and its metadata costs roughly the same whether the file holds ten rows or ten million, so once files get small that fixed cost dominates and the filesystem's directory-listing overhead starts to show up too.

SituationChooseWhy
Small dataset, exploring aloneone Parquet filePartitioning overhead outweighs the pruning benefit below a few hundred MB
Repeated queries filtered by date and/or a categorypartition by those columnsMatches the pruning to how you actually query — this lab's case
A column with millions of distinct values (trade ID, raw tick timestamp)never a partition columnProduces one file per value — the small-files problem, deliberately
⚠️ Pitfall — "more partitions is always more parallelism"

More files does mean more units of work an engine could spread across threads — but only up to the point where the fixed cost of opening a file (its footer, its schema, its directory entry) stops being negligible next to the data inside it. Partition by what you filter on, to a size in the tens-to-low-hundreds of MB per file; do not partition by everything you might one day group by.

4.5.7 When kdb+ or a managed warehouse earns its cost

Everything above runs on one laptop for free. Two other tools exist for when "one laptop" stops being the right answer — worth recognising, not worth a hands-on lab here.

kdb+ (rebranded KDB-X by its vendor KX in 2025-26) is a proprietary column-oriented time-series database built around the array language q, purpose-built for the thing this lab's stack is not: ingesting a live tick feed at very high message rates with almost no latency and querying it seconds later. Production kdb+ systems on a trading floor typically split the job into a tickerplant that captures and logs the incoming feed, a real-time database (RDB) that holds the current day in memory for intraday queries, and a historical database (HDB) of prior days partitioned on disk by date — an architecture built for the same reason this session partitions by year: so a query for "today" or "last Tuesday" never has to touch the rest. As of 2026, KX offers a free Community Edition (personal and light commercial use, capped at 16 GB of RAM for a single instance) and a Personal Edition for individual non-commercial use; production deployment at real tick-capture scale is a paid, usage-metered commercial licence. That licence, plus q's own learning curve, is why most research desks reach for kdb+ only once they are actually capturing ticks in real time, not for historical research on daily or minute bars.

A managed warehouse — Snowflake, BigQuery, or a hosted ClickHouse — solves a different problem: not raw single-query speed, but many people and many jobs querying the same governed dataset concurrently, with someone else responsible for uptime, backups, access control and scaling storage independently of compute. Session 4.2 — Point-in-Time Data & Data Biases's point-in-time discipline and Session 4.3 — Corporate Actions, Security Master & Continuous Futures's security master both get harder, not easier, once a dozen researchers share one dataset — a managed warehouse (or a team-scale variant of this session's own stack, like the open-source Parquet-based ArcticDB from Man Group, whose commercial use needs a licence beyond its Business Source terms) is what makes that sharing safe rather than a source of silently different answers.

💡 Tip — don't reach for either on day one

A single laptop with a partitioned Parquet dataset comfortably handles tens of millions of rows and tens of gigabytes — most of a solo researcher's or small team's career, and everything this course's later labs need. Reach for kdb+ when the problem is genuinely real-time tick capture; reach for a managed warehouse when the problem is genuinely concurrent, shared, governed access. Reaching for either to solve "my CSV is slow" is solving the wrong problem.

4.5.8 Glossary · Check yourself · Go deeper

Parquet — a columnar file format: compressed, self-describing, and splittable into many files.
Apache Arrow — a columnar format for data in memory, shared across libraries and languages without copying.
DuckDB — an embedded, server-free SQL engine that reads Parquet directly and executes over Arrow.
polars — a Rust-based DataFrame library with a lazy, multi-threaded query engine built around Arrow.
Lazy evaluation — building a query plan first and running it only when the result is requested, so filters and column selections can be pushed into the scan.
Partitioning — writing a dataset as many files in directories named after column values, so a filtering query can skip whole files.
Columnar storage — laying data out column-by-column on disk or in memory, so a query can decode only the columns it needs.
kdb+ — a proprietary column-oriented time-series database (language q), built for high-rate tick capture and low-latency query.

Check yourself

1. A single Parquet file is already columnar and compressed. Why does partitioning it further make the lab's query another order of magnitude faster?
Columnar format only helps with column pruning — decoding fewer of the file's fields. It does nothing about row pruning: a single file still has to be opened and its matching row groups scanned in full. Partitioning adds a second, independent axis of savings (skip whole files by directory name) that multiplies with column pruning rather than substituting for it — which is exactly why §4.5.4 measures roughly a 12-19× gap between "Parquet, one file" and "Parquet, partitioned."
2. You partition a dataset by trade_id because "then every query finds its row instantly." What goes wrong?
A high-cardinality column produces one partition per distinct value — potentially millions of tiny files. Reading even a small slice now means opening thousands of files, each paying the same fixed footer/metadata/open() cost regardless of how little data it holds; §4.5.5 measures a 7× slowdown from turning one file into 150. Partition on the handful of columns your queries actually filter on, not on the column with the most detail.
3. Your team's shared research dataset gets slow and inconsistent once eight people query it at once from their own laptops. Is the fix kdb+?
No — that is a concurrency and governance problem (many readers, one source of truth, someone accountable for access and uptime), which is what a managed warehouse solves. kdb+ solves a different problem: very high-rate, low-latency live tick capture. Reaching for either tool without matching it to the actual bottleneck just adds licensing cost and operational complexity.
4. polars' scan_parquet(...).filter(...) hasn't touched disk yet, even though you wrote the filter. Why does that matter?
Because nothing has executed, the optimiser can still see the whole query when it finally runs at .collect() — including a later .select() — and push both the filter and the column selection down into the scan itself. If filter ran eagerly the moment it was called, the engine would already have decoded every column of every row before it knew which ones the rest of the query needed.
5. The lab reports DuckDB at roughly 45× faster than naive CSV on this machine. Should you expect exactly that number on yours?
No. The ratio is expected to stay large and in the same rough range, because it comes from how much less data is read (a property of the query and the partitioning, not the hardware); the exact millisecond figures depend on disk speed, core count, background load and whether the OS has already cached the files. That is why the lab asserts a wide, conservative margin (5×, not 126×) rather than the specific number it happens to measure.
