Lab: Build Your Research Data Lake

Every lab from here on needs the same three things: prices that don't lie about splits, joins that don't peek at the future, and a place to put the result that a later session can just query. 4.6.1 What a research data lake is

Every lab in this course reads data from somewhere. This section names the three jobs that "somewhere" has to do, and why skipping any one of them shows up as a bug three sessions later.

Forget the enterprise-scale meaning of "data lake." For one researcher, a research data lake is nothing more than a folder of Session 4.5 files on a laptop, built by one script that can be rerun from nothing, plus a couple of query views on top. The alternative — reading a raw CSV fresh in every notebook — feels simpler until the second notebook disagrees with the first about a stock split, and there is no record of which one is right.

The lake in this lab has three tiers, and each one has exactly one job. Raw landing holds the vendor feed exactly as it arrived, including its mistakes — a raw feed showing a fake −50% return on a split day is not a bug in the feed, it is what a real feed looks like. Curated is where Session 4.3's corporate-action adjustment and Session 4.4's as-of joins and bars run, and where a data contract is enforced before anything is written. Query views — a DuckDB view and a polars lazy frame over the same Parquet files — are the only tier a later lab is ever allowed to touch.

Each tier exists because of a specific way research goes wrong without it. Skip the raw tier and there is no way to tell, months later, whether a strange number came from the market or from a script that overwrote its own input. Skip curation and every notebook re-derives its own version of "adjusted," each subtly different. Skip a query tier and every lab pays the cost of re-reading and re-parsing the same files, in whatever ad hoc way that lab's author chose that day. None of this is really about performance — a few years of daily bars for a handful of symbols fits in memory twice over. It is about a research team, even a team of one working across many sessions, being able to trust a number without re-deriving it from scratch.

📌 Key idea — the lake is not the strategy

Nothing in this session predicts a return. Its job is narrower and, in practice, more consequential: if a later unit's strategy looks brilliant because of a stock split nobody adjusted for, the bug will not be in the strategy code — it will be here, in a tier that was supposed to have caught it.

4.6.2 The pipeline, end to end

Five stages turn a raw feed into something a query can trust. Each one has exactly one classic bug, and this lab's asserts exist to catch it.

StageWhat runsWhat it prevents
1 · Ingestthe raw feed lands in a git-ignored cache, byte for bytesilent edits to history
2 · Adjustback-adjustment, applying Session 4.3's adjustment factorsfake crashes from splits and dividends
3 · Validatethe curated table is checked against its data contracta bad row shipping to every later lab
4 · Bar + writean as-of join for reference data, bars, then a partitioned writea join that peeks at the future; one unqueryable file
5 · Querya DuckDB view and a polars lazy frame over the same filesscanning bytes a query does not need

Raw landing being immutable is the load-bearing rule in this whole diagram, and it is worth saying why. If a bug in the adjustment stage is discovered next month, the fix is to rerun stages 2 through 5 against the same raw files and get a corrected curated table — nothing upstream needs to be re-fetched or reconstructed from memory. If the raw feed itself is allowed to be edited in place — a "quick fix" for one bad row, applied directly to the landing file — that guarantee is gone: nobody can prove, later, whether today's raw file is what the vendor actually sent. The discipline is the same one an append-only event log gives a production system: never mutate history, only add stages that read it.

💡 Looking ahead

Everything after Unit 4 assumes this pipeline already ran. A strategy session in Session 5.1 and onward reads the query tier and never touches raw vendor files — the same discipline a production trading system needs between its market-data feed and its signal code.

4.6.3 Corporate actions, applied

A stock split is one line in a corporate-actions feed and, if you ignore it, a manufactured crash in every return you compute afterwards.

ALPHA, one of this lab's three synthetic symbols, does a 2-for-1 split partway through its three-year window. The raw feed does exactly what a real vendor feed does: from the ex-date on, the price is halved and the share volume doubles, with nothing flagging that a split happened. On its own, that single day's raw return is −50.8% — a number no strategy earned and no risk model should ever see.

Fixing it is Session 4.3's job: an adjustment factor, a multiplier that is 1.0 after the corporate action and 1/ratio1/\text{ratio} before it, so the whole history reads in today's share terms. Multiplying raw prices by that factor is a ratio adjustment; carrying it back through the full history is a back-adjustment, producing the adjusted price this lake actually stores. Applied correctly, the same day's adjusted return falls to an ordinary −1.6% — this lab's own bug: an early draft applied the factor the wrong way round and multiplied by the ratio instead of dividing, which is exactly what the assert in the code below catches.

# 1.0 before the event would UNDO nothing; 1/ratio brings the pre-split leg down
# to today's post-split terms, matching the level the raw feed already shows after the split.
def adjustment_factor(n, event_day, ratio):
    factor = np.ones(n)
    factor[:event_day] = 1.0 / ratio
    return factor

adjusted_price = raw_price * adjustment_factor(len(raw_price), SPLIT_DAY, SPLIT_RATIO)

The direction is easy to get backward, and worth checking by reasoning about units rather than memorising a rule. A 2-for-1 split doubles the number of shares outstanding and halves the price per share; the company's total value on the day does not change. So a price series expressed consistently in today's shares must show the pre-split leg at half its recorded level, not double it — dividing, not multiplying. Go the other way, as this lab's own first draft did, and the adjusted series records the company as having lost three-quarters of its value overnight, which is a worse bug than the one it was supposed to fix. A cash dividend is the other everyday corporate action, adjusted by a small multiplicative factor on the ex-dividend date rather than a large one at a split; Session 4.3 covers both in full, along with mergers, spin-offs and the identifier changes they bring.

The same window has a second, quieter problem: BETA is renamed BETA2 partway through — same company, new ticker. A pipeline that joins on the ticker string alone would see two different symbols with adjacent, unrelated histories. A Session 4.3 security master gives every ticker string a permanent security identifier that survives the rename, so this lake's curated table carries 4 tickers but only 3 underlying securities — the number every later join should actually use.

🧭 Margin note — a security identifier is a primary key

An engineer would never join two tables on a user's display name, because names change. A ticker is a display name for a company; the security identifier is the primary key. Session 4.3 builds the full security master; this lab only needs to remember never to join on the string that can change.

4.6.4 As-of joins & bars, applied

A join that is even slightly wrong about time turns clean history into a leak from the future.

This lake attaches a quarterly index-committee review — whether each security counts as an index member — to the daily curated table. Getting the review "as of" a given date right is Session 4.4's job: an as-of join matches each row to the most recent review on or before its timestamp, and never a later one. Pandas' merge_asof makes the correct version, direction="backward", and the tempting shortcut, direction="nearest", one keyword apart — and on this lake's 36 quarterly reviews, the shortcut matches a review that has not happened yet on 1,023 of 2,271 rows, changing the membership flag on 559 of them. That is exactly the shape of look-ahead bias: information a backtest could not have had, arriving early.

💡 Tip — read the direction keyword every time

nearest is the right choice for genuinely undated reference data, like rounding a trade to the nearest quote. For anything that becomes known on a date — a review, a filing, a restated number — the only safe default is backward.

The same table also feeds Session 4.4's bars. A daily row is a time bar: one per calendar day, regardless of how much traded. A dollar bar instead closes whenever cumulative traded value crosses a threshold, and a volume bar does the same on shares traded — both sample by information, not by the clock (López de Prado, 2018). ALPHA's 757 time bars became 453 dollar bars and 466 volume bars once this lab made trading volume rise with the size of the day's move, exactly as busy markets do: a dollar bar closes every 2.0 days near the split, against 2.7 days in quieter stretches.

Sampling ruleBar count on ALPHAAdapts to activity?
Time bar — one per day757no — every day gets one, however quiet
Volume bar — every N shares traded466yes
Dollar bar — every $N traded453yes, and robust to the price level itself

The "nearest" shortcut earns its keep in an ordinary pandas exercise — matching a trade to the closest quote a few milliseconds away rarely cares which side of "closest" it fell on. It stops being harmless the moment the right-hand table is something that becomes true on a date, like an index review, a filing or a restated number, because "nearest" has no concept of before and after: it will happily hand a row of March data a fact that was only announced in June. This lab's own numbers show the effect is not rare on a quarterly review schedule — it does not need daily reviews or an adversarial dataset to matter, only the wrong keyword. Information-driven bars earn their place for a related reason: López de Prado (2018) reports that dollar bars bring a return series closer to independent and identically distributed than fixed-time bars do, which matters because most of the statistical machinery later units rely on — standard errors, hypothesis tests, the Sharpe ratio's own confidence interval — assumes exactly that.

4.6.5 The storage layer, applied

The curated table is written once, as files a query engine can prune without ever opening them.

The curated table lands as Session 4.5's Parquet — a columnar, compressed, typed file format — partitioned by symbol in the Hive convention (symbol=ALPHA/…). Written this way, the same rows that take 162,060 bytes as CSV take 77,724 bytes as partitioned Parquet — about 2.1× smaller on this small a table, and the gap only grows with more history, because Parquet's column-oriented, dictionary-encoded layout is exactly what makes a query engine's next trick possible (Melnik et al., 2010).

Session 4.5's DuckDB reads the partitioned directory directly: a query that filters on symbol skips every file whose partition value cannot match, without opening it. This lab checks that literally — a view over all 2,271 rows returns exactly 757 rows for one symbol, the same count pandas gives directly from memory. polars' lazy evaluation does the analogous thing on the read side: a scan_parquet(...).filter(...).select(...) pipeline builds a query plan and only touches bytes once .collect() runs, with the filter and the column projection pushed down ahead of it. Cross-checking a polars-lazy mean against the same pandas column agrees to within 0.0e+00 — two independent engines, one number.

None of this needs its own conversion step. Writing the curated pandas table to Parquet in this lab goes through a pyarrow.Table first — the same columnar, in-memory format DuckDB and polars both read and write natively, so a value moves between pandas, Arrow, DuckDB and polars without ever being serialised to text or copied through a row-by-row loop. Partitioning by symbol, rather than by date, is a bet on how this lake is actually queried: almost every research question in this course asks "give me this symbol's history," while "give me every symbol on this one day" is rare. A production system ingesting live ticks would likely choose the opposite split, or partition by both — the right partition key follows the query pattern, not a rule.

🧭 Margin note — when Parquet plus DuckDB is not enough

This stack comfortably serves one researcher's history on a laptop. Sell-side desks and market-makers querying tick data at nanosecond resolution across years often reach for kdb+ instead — a proprietary, in-memory time-series database with real licensing costs. Session 4.5 makes that trade-off explicit; nothing in this course needs it.

4.6.6 Quality gates, lineage & idempotency

This is the part only this session owns: the discipline that makes a pipeline safe to rerun, and a table safe to trust without re-deriving it.

A data contract is the schema and the rules a curated table promises to satisfy: which columns must exist, which may never be null, and which values must make sense. A data quality check tests real data against that contract and reports every violation, not just the first. This lab's contract is six columns, non-null keys, no duplicate (date, symbol) pairs, ascending timestamps, and positive prices, non-negative volume and a positive adjustment factor — checked once on the clean curated table (0 violations) and then again on a copy with four deliberately injected problems, which the same check catches all 4 of.

def check_quality(df):
    # returns every violation, not just the first — a data contract you can act on
    problems = []
    if df["date"].isna().any() or df["symbol"].isna().any():
        problems.append("null key column")
    if df.duplicated(["date", "symbol"]).any():
        problems.append("duplicate (date, symbol) rows")
    # … ascending timestamps, positive price, non-negative volume, positive adj_factor
    return problems
CheckCatchesWhy it matters
required columns presenta stage that silently dropped a columna KeyError three files away, not here
no null keysa row nobody can join or partitionnulls in a partition column corrupt the layout
no duplicate (date, symbol)a row written twice by a reruna bar or a return counted twice

An idempotent pipeline run twice with the same inputs and the same seed either writes byte-identical output or — better — recognises that nothing changed and skips the rewrite. This lab fingerprints its parameters and its seed together, hashes the curated table's content with quantnb.repro.content_fingerprint, and only rebuilds the Parquet dataset when either has changed. The first call reports built; the second, with nothing changed, reports skipped (already built) — calling the pipeline a second time is a question, not a rebuild. Data lineage is the record that makes that question answerable at all: a small manifest, keyed by fingerprint, logging the pipeline version, the parameters, the seed and the row count of every build that ever ran, so a suspicious number downstream can be traced back to the exact run that produced it.

This is Session 1.5's run manifest — commit, package versions, a data fingerprint and a random seed, recorded so one lab's result can be reproduced — applied to a dataset that gets rebuilt many times rather than to a single script run once. Session 1.5's manifest answers "what produced this number"; this lake's lineage answers the same question for "what produced these files," and the two ideas share a mechanism on purpose: a data cache keeps expensive results around, keyed by exactly the inputs that determine them, and both a run and a data-lake build are just results that happen to be a folder of Parquet files instead of a printed metric.

4.6.7 Proving it works

A lake is only useful if a research query on it gives an answer you can trust — and this one shows exactly what happens when it doesn't.

The whole point of the last six sections is a query. Reading ALPHA's history back through the query tier and computing a Sharpe ratio and a drawdown — synthetic excess returns, risk-free rate 0 — on the raw feed and on the curated, adjusted table gives two very different answers to the same question.

MetricRaw feed (unadjusted)Curated (adjusted)
Sharpe ratio−0.020.76
Maximum drawdown−52.7%−19.0%
Return on the split day−50.8%−1.6%

Nothing about ALPHA's underlying business changed on the split day. The raw-feed column is not a worse investment — it is the same investment measured with a bug. the Sharpe ratio and the drawdown both belong to Session 2.3; whether they mean anything belongs to this lake.

⚠️ Pitfall — "the vendor already adjusts for splits"

Some vendors do, for some fields, some of the time: a "close" column and an "adjusted close" column sitting side by side in the same file, with nothing in the schema saying which later code was written against. The moment a new script points at the unadjusted column by mistake — or a data provider quietly changes which column carries the adjustment — this exact bug reappears, and it will not raise an exception; it will just make one symbol's history look like it crashed. The fix is never to trust a claim about a column's name. It is to check the contract yourself, the way check_quality does here, every time a new feed enters the raw tier — trust the assert, not the label.

4.6.9 Glossary · Check yourself · Go deeper

Data contract — the schema and rules a curated table promises to satisfy: required columns, non-null keys, and value ranges every later query can rely on without re-checking them.
Data quality check — code that tests real data against a data contract and reports every violation it finds, run before the data is trusted downstream.
Idempotent pipeline — a pipeline that, run twice with the same inputs and the same seed, either produces byte-identical output or detects that nothing changed and skips the rewrite.
Data lineage — a record of which inputs, parameters, seed and pipeline version produced a given build, so a downstream number can be traced back to the run that made it.

Check yourself

1. Why does the lake write curated data as partitioned Parquet with a `symbol` column, rather than one large CSV?
Partitioning by symbol lets a query engine skip every file that cannot match a `WHERE symbol = …` filter without opening it, and Parquet's columnar layout lets it read only the columns a query needs. A single CSV forces a full scan and a full row parse every time — one file, but no gates to skip through it.
2. A colleague reruns the pipeline twice in a row and is annoyed that the second run "did nothing." Is that a bug?
No — it is the point. An idempotent pipeline recognises that the fingerprint of the parameters, seed and data content has not changed, and reports a verified no-op rather than silently rewriting the same bytes. A pipeline that instead rewrites (and possibly reorders or reformats) identical data on every run makes "did the data change?" unanswerable from the files alone.
3. What happens if you compute a Sharpe ratio directly on ALPHA's raw, unadjusted prices?
The 2-for-1 split alone manufactures a one-day return of about −50.8% and a maximum drawdown of −52.7% that has nothing to do with the business. The adjusted series instead shows a maximum drawdown of −19.0% — the number that actually reflects what happened.
4. Why does a lineage manifest record the seed alongside the parameters?
Because this lake is built from synthetic data, the seed is part of what determines the content — two runs with identical parameters but different seeds produce different (equally valid) data. A cache key or a fingerprint that omits the seed would treat two different datasets as the same one, and an idempotency check built on it would wrongly skip a rebuild.
5. An as-of join uses `direction="nearest"` instead of `direction="backward"`. What could go wrong, concretely?
`nearest` can match a row to a review, filing or price that has not happened yet as of that row's date — a look-ahead leak. On this lab's own panel, a nearest-match join picks a future review on 1,023 of 2,271 rows, changing the resulting value on 559 of them.
