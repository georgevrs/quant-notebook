Point-in-Time Data & Data Biases

A backtest is only as honest as what its data could have shown you on each historical date — never what your database shows you today. This session builds three of the classic ways a backtest quietly lies about the past — a survivorship-filtered universe, a restated fundamental and a backfilled track record — each one measured side by side against its point-in-time-correct twin, so the manufactured alpha shows up in a chart instead of in a promise. The core move: every fact has two dates, and a decision dated t may only use facts whose knowledge date has already passed.

4.2.1 Every fact has two dates

A number in a database is not just a value — it is a value plus a story about when the world learned it. Confuse the two dates and every later calculation is quietly wrong.

Take one very ordinary fact: a company's quarterly revenue growth. It has a reference date — the period it describes, say the quarter ending 2024-06-30 — and a knowledge date — the date the number actually became public, typically weeks later once the filing is made. Most vendor databases store only the reference date and the latest value, which quietly assumes the two dates are the same. They almost never are, and the gap between them is where every bias in this session lives.

Point-in-time data is data reconstructed exactly as it was knowable on a given historical date — not as it looks with hindsight today. A data vintage is one dated snapshot of a field as it stood on a specific publication date, before any later revision; a field can have many vintages over its life. When a company (or a statistical agency) later corrects a previously published figure, that correction is a restatement — a new vintage that replaces, but does not erase, the old one. Query a live database for "revenue growth, Q2 2024" today and you get the latest vintage — the restated number — even if you are pretending to stand on a date before the restatement existed. That silent substitution is look-ahead bias: using, at decision time t, any fact whose knowledge date has not yet arrived.

If you have ever built a machine-learning pipeline, you already know this failure mode by another name: train/test leakage. A point-in-time query is simply a strict time-based split applied to a live decision instead of a training run — nothing dated after the cutoff is allowed to influence it, no matter how obviously "correct" or "helpful" it would have been. The reason vendors default to the leaky version is mundane, not malicious: storing only the current value of every field is far cheaper and simpler than storing every revision ever made to it, and for most non-research uses — a dashboard, a risk report as of today, a trader's screen — the current value is exactly what you want. The trouble starts only when that same "current" table is reused for something it was never built for: a simulation of a decision made in the past.

This is not unique to company fundamentals. Government statistical agencies revise macro releases constantly — an initial GDP estimate, a payrolls number, or an inflation print is routinely revised for months or years after first release, sometimes by more than the number itself. The Federal Reserve Bank of Philadelphia's ALFRED database exists specifically to preserve every vintage of these series rather than only the latest one, which is precisely why a real-time macro forecaster reaches for it instead of a standard FRED query [2].

📌 Key idea

A backtest is a simulation of a decision made on date t. It is only honest if every input it uses had a knowledge date on or before t. Point-in-time data is the discipline of keeping every vintage of every fact so that question is even answerable.

4.2.2 How a backtest quietly rewrites history

Nobody sets out to cheat. The default research workflow — query the vendor for what exists right now — manufactures three separate biases as an accidental side effect.

Open a terminal, pull a universe and a fundamentals table from your usual vendor, and backtest a strategy "since inception." That single habit is the workflow below, and each of its five steps has exactly one classic bug hiding in it.

Step 2 is survivorship bias: building the historical universe from names listed today silently drops every name that failed, was acquired, or was struck off along the way — before you ever look at a single return. Step 3 is look-ahead bias in its restatement flavour, covered in §4.2.3. A cousin of both lives one level up, before a name is even in the database at all: backfill bias is a bias of selective entry rather than selective exit — a fund, an index or a coin only gets its historical track record added once someone judges it worth listing, so the ones that never made the cut leave no trace at all.

Step 2 is worth dwelling on because it is the single most common way a beginner (and plenty of professionals) accidentally builds a biased universe, and it is completely invisible from the code. "Pull the current S&P 500 constituents and get ten years of history for each" is a perfectly ordinary line of research code; nothing about it errors, warns, or looks wrong in a code review. The problem is entirely in what that query is silently NOT asking for: the names that were removed from the index over those ten years for going bankrupt, being acquired below their pre-announcement price, or simply falling out on size — precisely the outcomes a strategy is supposed to be tested against. Data vendors know this, which is why point-in-time index-membership files (who was actually IN the index on each historical date, not just who is in it today) are usually sold as a separate, pricier product from a plain historical-prices feed — a licensing distinction Session 4.1 — The Data Landscape, Vendors & Licensing covers from the vendor side.

4.2.3 Naming and sizing the damage

Each bias has a clean formal description and a documented order of magnitude — worth knowing so you can sanity-check whether a result is too good to be true.

Vintages, formally

Write Dv(s)D_v(s) for the value of a fact with reference date ss, as published in vintage vv (the calendar date that value was released). A query issued on date tt can only see vintages already released, so it sees:

Dt(s)=Dv(t)(s),v(t)=max⁡{v≤t}D_t(s) = D_{v(t)}(s), \qquad v(t) = \max\{\, v \le t \,\}

A point-in-time query at decision date tt always uses Dv(t)(s)D_{v(t)}(s). Look-ahead bias is using Dv′(s)D_{v'}(s) for some vintage v′>tv' \gt t — a vintage that, as of tt, does not exist yet. This is the general shape §4.4 turns into runnable code.

Survivorship bias, as an approximation

Let π\pi be the probability that a given name is delisted for cause before a horizon of YY years, R‾surv\bar R_{\text{surv}} the average per-period return of names that never delist, and R‾delist\bar R_{\text{delist}} the average return earned in a name's delisting period (the delisting return itself, usually sharply negative). The true, point-in-time average return blends both groups; a survivorship-filtered estimate reports only the first:

R‾surv−R‾PIT≈π(R‾surv−R‾delist)>0\bar R_{\text{surv}} - \bar R_{\text{PIT}} \;\approx\; \pi \left( \bar R_{\text{surv}} - \bar R_{\text{delist}} \right) \;\gt\; 0

This is a one-period intuition, not an exact law for a rebalanced, multi-period index — compounding many periods of selective removal has no clean closed form, which is exactly why §4.2.4's lab measures it with Monte Carlo instead of asserting this formula directly. The sign is no accident: Brown, Goetzmann, Ibbotson & Ross's foundational result [1] is precisely that conditioning a sample on survival to a horizon induces a spurious relationship between past performance and the appearance of skill, because low returns raise the hazard of being the one that doesn't survive.

Notice what this formula does and does not say. It does not say survivorship bias only matters for small, distressed companies — it says the bias is proportional to π\pi, the fraction that fails to survive, whatever the universe. A large-cap, developed-market index has a small π\pi over most horizons, so the bias tends to be modest; a universe of early-stage biotech names, pre-revenue crypto tokens, or emerging-market small caps can have a π\pi large enough to dominate the entire result — which is exactly the gap between the CTA-fund row and the crypto row in the table below: the same mechanism, at two very different values of π\pi. For a concrete sense of scale, Malkiel's study of US equity mutual funds found roughly 3% of funds disappearing from the sample every single year [4] — over a 15-year backtest that alone is a π\pi above 30%, before a single stock-picking decision is even made.

Restatement bias, exactly

A fundamental signal has a true, unobservable component qq (standardised) that drives next period's return r=βq+εr = \beta q + \varepsilon. Nobody measures qq directly — only a noisy version qˆ=q+u\hat q = q + u, with measurement noise uu of variance σu2\sigma_u^2. Classical attenuation gives:

Corr⁡(qˆ,r)=Corr⁡(q,r)1+σu2\Corr(\hat q, r) = \frac{\Corr(q, r)}{\sqrt{1 + \sigma_u^2}}

A restatement does not change which dates are involved — only how much noise σu\sigma_u it has washed out. Less noise means a bigger, more attractive correlation, even though nobody could have measured it that cleanly at the time. §4.2.4 measures both sides of this formula directly.

It helps to picture a noisy signal as a photograph taken through fog: the shape underneath is genuinely there, correlated with the truth, but the fog caps how sharp that correlation can ever look. A restatement doesn't remove the fog by giving you a better camera on the original date — it removes it by waiting months or years for the weather to clear, then handing you a crisp photo and letting you pretend it was always this clear. That is the entire mechanism, and it is worth separating carefully from the more familiar idea of a reporting lag (a value simply arriving late, which Session 4.4 — Time, Calendars, As-of Joins & Bars handles with an as-of join): a lag is a timing problem with a timing fix; restatement bias is a noise problem that a timing fix alone cannot touch, because the as-reported number was never going to be as accurate as the restated one, no matter how carefully you respect its knowledge date.

Backfill bias, exactly

If a database only ever lists the top fraction pp of a population, ranked by some track record r‾∼𝒩(μ,σr‾2)\bar r \sim \mathcal N(\mu, \sigma_{\bar r}^2), the listed subset's average is not μ\mu but the mean of a truncated normal above its (1−p)(1-p) quantile:

𝔼[r‾|listed]=μ+σr‾ϕ(zp)p,zp=Φ−1(1−p)\E[\bar r \mid \text{listed}] = \mu + \sigma_{\bar r}\,\frac{\phi(z_p)}{p}, \qquad z_p = \Phi^{-1}(1-p)

where ϕ\phi and Φ\Phi are the standard normal density and CDF. This is the same selection mathematics behind the False Strategy Theorem you will meet again in Session 6.7 — Overfitting Statistics: PSR, DSR, MinTRL & PBO: measuring an average after conditioning on an outcome correlated with that average is guaranteed to be optimistic, whether the thing you selected on is "which strategies I kept testing" or "which funds got listed."

The two formulas above look unrelated — one is a correlation shrinking under measurement noise, the other is a mean shifting under truncation — but they share the same shape as the survivorship approximation before them: in every case, a filter correlated with the outcome sits between the population and what you get to observe. Look-ahead bias filters on time (only vintages published early enough should have been visible); survivorship bias filters on which names still exist; backfill bias filters on which candidates were ever worth writing down. Different filters, identical arithmetic: whenever the filter and the outcome are correlated, the average you observe is not the average that existed.

🧭 Margin note — exit bias vs. entry bias

Survivorship bias silently drops bad exits (names that failed along the way); backfill bias silently drops bad non-entries (candidates that never earned a listing). They are mirror images of the same mistake — measuring a population using only the members who made it through some filter correlated with the outcome you're measuring.

4.2.4 In code: querying the past honestly

The fix is structural, not statistical: store every vintage, and always query "as of" a decision date. Here it is in DuckDB, and then two full backtests built the honest way and the naive way, side by side.

A minimal point-in-time data table needs only a reference date, a knowledge date and a value per row — never a "current value" column that a restatement can silently overwrite:

# a bitemporal table: one row per VINTAGE, not one row per fact
con.execute("""
    INSERT INTO fundamentals_vintages VALUES
        ('SYNTH', '2024Q2', DATE '2024-08-09', 0.0410, FALSE),  -- as first filed
        ('SYNTH', '2024Q2', DATE '2025-11-12', 0.0270, TRUE)    -- restated ~15 months later
""")

# naive: "give me the latest value" — silently the restatement, from 15 months in the future
naive = con.execute("""SELECT value FROM fundamentals_vintages
    WHERE ticker='SYNTH' AND ref_quarter='2024Q2' ORDER BY knowledge_date DESC LIMIT 1""").fetchone()

# point-in-time: "give me the latest value KNOWN as of asof" — the original filing
pit = con.execute("""SELECT value FROM fundamentals_vintages
    WHERE ticker='SYNTH' AND ref_quarter='2024Q2' AND knowledge_date <= ?
    ORDER BY knowledge_date DESC LIMIT 1""", [asof]).fetchone()

Querying as of 2024-09-01, right after the original filing, the naive query returns 2.70% — the value from 15 months in the future — while the point-in-time query correctly returns 4.10%, the number that actually existed that day. Nothing about the SQL is exotic; the discipline is remembering to add the knowledge_date <= ? filter every single time, which is exactly what a real as-of join automates (Session 4.4 — Time, Calendars, As-of Joins & Bars) once your tables live in Parquet/DuckDB rather than a spreadsheet of "current" values.

💡 Tip

Keep vintages, never overwrite: store a new row for every revision, and let knowledge_date — not "today's value" — be the only thing a query filters on. Session 4.5 — The Research Storage Stack covers the storage side of this properly.

Experiment 1 — survivorship: a look-ahead vs. point-in-time backtest, side by side

200 synthetic 15-year universes of 150 stocks each. Every stock's monthly hazard of delisting rises with how badly it has done over the trailing year — distress precedes delisting, as it does in real markets — and on delisting we draw a delisting return: mostly a harsh, distress-flavoured loss, occasionally a takeover premium. On average, only 35% of names are still listed after 15 years — a small-cap-like universe with heavy churn, chosen deliberately to make the mechanism visible; real broad equity indices turn over far more slowly (see the table in §4.2.3).

We then build the same equal-weight portfolio two ways from the same simulated world: point-in-time correct (every name still listed each month, including its harsh return in the month it delists) and survivorship-filtered (only the names still listed at the very end, backtested "since inception"):

The point-in-time-correct CAGR is 7.3% a year; the survivorship-filtered version reports 12.3% — a gap of 4.9 percentage points a year, averaged across all 200 universes, that comes from nothing but which tickers were allowed into the average. That gap is real at 0.09% standard error — more than 50 standard errors from zero — never a property of one lucky universe. The survivorship-filtered version doesn't only look more profitable: its maximum drawdown of −4.1% is milder than the true −4.5%, understating risk on top of overstating return. (This synthetic universe has no shared market factor, so both curves are far smoother than a real equity portfolio — the point is the gap between the columns, not the absolute Sharpe of 1.8 vs. 2.4.)

Experiment 2 — restatement: the same signal, sorted on two versions of the same data

A synthetic "quality" score drives next quarter's return, exactly as in §4.2.3's formula. We sort a long-short quintile portfolio on two measurements of the identical underlying quality, at the identical rebalance dates — only the amount of noise differs: an as-reported version (noisy, exactly what a filing gives you at the time) and a restated version (cleaner, only knowable years later).

The as-reported, achievable information coefficient is 3.7% — small, but real, and it matches the attenuation formula's prediction of 3.6%. Swap in the restated numbers, changing nothing about the dates, and the same correlation more than doubles to 7.6% (formula: 7.6%). The long-short Sharpe follows the same path: 0.51 point-in-time versus 1.06 using restated data — a gap of 0.55 that is not luck (it holds at more than 20 standard errors across 200 independent universes). Nothing about the timing changed; the restated number is simply a more accurate ruler than anyone had on the rebalance date, and sorting on it manufactures a Sharpe ratio you could never have earned live.

Notice the shape of what just happened across both experiments: nothing about the SIMULATED WORLD changed between the two columns of either chart. Experiment 1 replayed the identical 200 universes and only changed which names were allowed into the average; Experiment 2 replayed the identical quarters and forward returns and only changed how much noise sat on the sorting signal. That is the whole point of building the biased and honest versions side by side from a single generative model — it isolates the bias from every other source of disagreement a real-world comparison would have (different markets, different periods, different luck), leaving only the one thing this session is about.

Experiment 3 — backfill: selection with zero true skill

3,000 hypothetical strategies each run a 24-month incubation with zero true edge. A database backfills the history of only the best 15% by incubation track record — exactly how a fund or coin database only ever shows you the ones good enough to get listed.

The full population's mean monthly return is −0.001% — correctly showing zero skill. The backfilled subset alone averages 1.27% a month, a bias of 1.27 percentage points a month (annualised, it looks like a 16%-a-year strategy) — matching the truncated-normal formula's prediction of 1.27% almost exactly. Every individual number in that database is genuine. The bias is entirely in which strategies got a row at all.

4.2.5 Where people go wrong

Two research setups can look identical in a code review and produce different truths, because the difference is a single WHERE clause nobody thought to ask for.

SituationChooseWhy
Backtesting a strategy since a historical datepoint-in-time data, every tableotherwise your Sharpe measures hindsight, not skill
Screening for a trade to place right nowtoday's "current" viewyou are not doing history — the latest, most accurate number is correct
Reading a fund's or coin's marketed track recordask whether it is backfilleda listed history that starts suspiciously well may only exist because it was good
⚠️ Pitfall — "I downloaded the S&P 500 list and got 20 years of history for each name"

This sentence describes a perfectly reasonable afternoon of work and a guaranteed survivorship bias. "The S&P 500 list" is today's membership; twenty years of history for those specific names silently excludes every constituent that was removed for failing, being acquired, or falling out of the index along the way. The fix is not "be more careful" — it is to use a vendor's point-in-time index-membership file, which records who was IN the index on each historical date, not just who is in it now.

Not every budget stretches to a proper point-in-time feed on day one, so it is worth knowing the cheaper, partial mitigations, in order of how much they buy you. Cheapest: apply a synthetic reporting lag to any fundamental field (shift it forward by a conservative 60–90 days before it enters a signal) — this does not fix restatement noise, but it removes the crudest look-ahead of using a quarter-end date as if it were a knowledge date. Next: whenever you can, source a delisted-name list for your universe (many exchanges publish one) and at minimum flag which of today's "clean" backtests are missing them, even if you cannot yet recover their exact returns. Most expensive but most correct: pay for the point-in-time product, which for equities is usually sold separately from a plain historical-price feed precisely because it costs the vendor far more to maintain — Session 4.1 — The Data Landscape, Vendors & Licensing explains why from the vendor's side. None of these substitutes for the real thing, but flagging the gap honestly is already better than the default, which is not noticing it exists.

4.2.7 Glossary · Check yourself · Go deeper

Point-in-time data — data reconstructed exactly as it was knowable on a given historical date, not as it looks with hindsight today.
Look-ahead bias — using, at decision time t, any fact whose knowledge date has not yet arrived — so a backtest quietly "sees the future."
Survivorship bias — building a historical universe only from entities that still exist today, silently dropping the ones that failed or were delisted along the way.
Restatement — a later revision to a previously published data value (an accounting correction, a revised GDP estimate) that a database may show in place of the original figure.
Data vintage — one dated snapshot of a field as it stood on a specific publication date, before any later revision.
Delisting return — the return assigned to a position when its security stops trading (bankruptcy, acquisition, exchange removal); omitting it manufactures survivorship bias.
Backfill bias — a bias of selective entry into a database: an entity's full history is added only once it is judged worth listing, so unsuccessful entities never appear at all (also called instant-history bias).

Check yourself

1. You query a vendor's fundamentals table on 2026-09-26 for "Acme Corp, Q1 2020 earnings" and get a number. What extra piece of metadata do you need before you can trust that number in a backtest dated 2020-05-01, and why?
You need the value's knowledge date — when it was actually published. A live query returns the latest vintage regardless of when you're pretending to stand; if that vintage's knowledge date is after 2020-05-01 (for example, a later restatement), using it on that backtest date is look-ahead bias, even though the reference date (Q1 2020) is correct.
2. In fig 4.2.2's workflow, step 2 ("today's universe") and step 3 ("today's fields") produce two different biases even though both stem from "just query the vendor for what exists now." Name each bias and say which is which.
Step 2 is survivorship bias — the set of names itself is wrong, because delisted names were dropped before you ever looked at a return. Step 3 is look-ahead bias via restatement — the names are right, but a field's value has been silently replaced by a later, more accurate vintage.
3. A colleague says: "Our fund database is survivor-bias-free — we never remove a fund once it stops reporting." Does that also rule out backfill bias? Why or why not?
No. Survivorship bias and backfill bias sit at opposite ends of a track record: never removing a fund once it stops reporting fixes the EXIT side (nothing disappears once it's in). Backfill bias happens at the ENTRY side — if the database only ever added a fund's history once it looked good enough to be worth adding, funds that never cleared that bar are missing entirely, regardless of how carefully exits are handled afterwards.
4. Section 4.2.4's naive DuckDB query and point-in-time query differ by exactly one clause. If you ran the naive query but happened to pick an asof date AFTER the restatement, would it still be biased?
Not for that specific date — after the restatement, both queries return the same value, because the latest vintage and the "as of" vintage coincide. The naive query is biased only when there is a vintage between your chosen asof and today; the bug is silent because it does nothing wrong until exactly the situation a backtest is built to explore: many historical dates, some of them before a later revision.
